# Standard GRC API — achados de campo, 2026-09-09

Onze achados levantados durante a integração de um consumidor externo, todos
medidos contra `https://standard-api.bekaa.eu/api/v1` entre 2026-09-08 e
2026-09-09, com uma chave de escopo `scf:read` e sem o header
`x-standard-tenant-id`.

Cada achado traz a chamada exata e o que ela devolveu, para ser reproduzível sem
contexto adicional. Onde há número, ele foi medido, não estimado.

**Ordem de leitura sugerida:** B11 e B9 primeiro. O primeiro decide se um cliente
certificado consegue usar a API para o caso de uso mais comum que ele tem; o
segundo quebrou em silêncio e provavelmente quebrou outros consumidores que ainda
não perceberam. O restante são defeitos localizados de endpoint.

---

## B11 — O Anexo A da ISO 27001 não está no catálogo

**Severidade: lacuna de produto, não defeito.** É o achado de maior consequência
comercial deste documento.

Verificado por três caminhos independentes:

**1. Não existe framework de Anexo A.** `GET /scf/frameworks` devolve 250
frameworks e exatamente um de ISO 27001 — `general-iso-27001-2022`. Os dois
únicos com "Annex" no nome são `emea-eu-cyber-resilience-act-annexes-2022` e
`emea-eu-nis2-annex-2024`, sem relação.

**2. O bundle STRM não carrega nenhum código de Anexo A.**

```
GET /scf/strm/lookup?fde_code=A.5.1    -> 200, count=0
GET /scf/strm/lookup?fde_code=A.5.15   -> 200, count=0
GET /scf/strm/lookup?fde_code=A.6.3    -> 200, count=0
GET /scf/strm/lookup?fde_code=A.7.1    -> 200, count=0
GET /scf/strm/lookup?fde_code=A.8.1    -> 200, count=0
GET /scf/strm/lookup?fde_code=A.8.34   -> 200, count=0
```

Seis códigos cobrindo os quatro temas da edição 2022. Nenhum dos 183 focal
documents responde.

**3. O próprio framework só publica cláusulas.**
`GET /scf/frameworks/{id}/requirements` para `general-iso-27001-2022` devolve
**148 requisitos, zero com prefixo `A.`**: `4.4`, `5.1`, `5.1(a)`,
`6.1.2(d)(3)`, `10.2(b)(2)`. É o sistema de gestão inteiro, e só ele.

**Por que isso pesa mais do que um endpoint quebrado.** Uma organização
certificada declara sua postura numa Declaração de Aplicabilidade, e uma SoA é
indexada pelo Anexo A — uma linha por controle, com aplicabilidade e
justificativa. É o artefato mais autoritativo que um SGSI produz e o formato que
auditor, hospital e questionário de segurança esperam.

As cláusulas 4 a 10 respondem *"vocês operam um SGSI?"*. O Anexo A responde
*"quais controles vocês aplicam?"* — que é a pergunta que os clientes de vocês
precisam responder aos clientes deles.

Sem Anexo A no crosswalk, o fluxo mais comum de um consumidor certificado — "aqui
está minha SoA, me diga o que ela cobre no SCF" — não tem por onde começar.

**Perguntas:** o Anexo A ficou de fora por licenciamento, por escopo, ou por não
ter chegado ainda? E o Anexo B da ISO 27701 (`B.8.2.1`…) tem o mesmo status? Um
consumidor que precise dos dois hoje tem de construir e manter esse crosswalk por
conta própria, o que reintroduz exatamente a classe de mapeamento não-oficial que
a re-importação do STRM veio eliminar.

## B9 — `framework_code` mudou de frase para slug, sem aviso

**Severidade: alta, e silenciosa — que é o que a torna grave.**

Até 2026-08-27 o campo trazia uma frase legível:

```
framework_code: "AICPA TSC 2017:2022 (used for SOC 2)"
```

Hoje traz um slug, e a frase migrou para `framework_name`:

```
framework_code: "general-aicpa-pmf-2020"
framework_name: "AICPA Privacy Management Framework (PMF)"
```

A modelagem nova é melhor. O problema é o caminho: **nenhum erro, nenhum aviso,
nenhuma nota de versão.** E a resposta de vocês à nossa Q13 estabeleceu
`framework_code` como parte de chave primária — ou seja, vocês sabiam que
consumidores chaveiam por ele.

O efeito num consumidor que persiste esse valor é uma junção que passa a casar
zero linhas. Um número derivado dessa junção não vira erro: vira soma sobre
conjunto vazio, indistinguível de um framework que ninguém avaliou. Levamos onze
dias para descobrir, e só medindo à mão.

**O que pedimos:** que uma mudança de forma num campo que vocês mesmos declararam
chave primária seja tratada como quebra de contrato — entrada no `CHANGELOG`, e de
preferência um período em que o valor antigo ainda resolva. E que a pergunta seja
respondida para quem for recurar: **o slug é estável entre versões de SCF, ou pode
mudar num próximo import?** Isso decide se um consumidor deve chavear por
`framework_code` ou por `framework_id`.

## B1 — `GET /scf/strm` devolve menos linhas que um único controle

**Severidade: alta.**

```
GET /scf/strm?limit=100&offset=0                      -> 200, count=64
GET /scf/strm?limit=100&offset=100                    -> 200, count=0
GET /scf/strm?scf_version_id=<versao corrente>        -> 200, count=64
GET /scf/strm?relationship_type=equal&limit=100       -> 200, count=8
GET /scf/strm/control/GOV-01                          -> 200, count=100
```

Um controle sozinho devolve mais linhas que a listagem da versão inteira. O bundle
carregou dezenas de milhares.

A listagem parece filtrar por algo não documentado — provavelmente
`organization_id`, que as linhas STRM carregam e que a busca cruza com a
organização da chave, enquanto a rota por controle não cruza.

Se for isso, vale a pergunta de produto: **por que uma linha do bundle oficial da
SCF é escopada por organização?** Ela é catálogo, não dado de cliente.

Sem essa rota funcionando, a única forma de obter o crosswalk é caminhar controle
a controle — cerca de 1.468 requisições, ~4 horas.

## B7 — `/scf/strm/control/{code}` não diz a qual framework a linha pertence

**Severidade: torna a rota inutilizável para mapeamento.**

```
GET /scf/strm/control/GOV-01?limit=500  -> 200, count=326
row: { strm_id, fde_code: "03.15.01.A", fde_name: "Policy and Procedures",
       relationship_type: "subset", relationship_strength: "1.000",
       rationale: "Functional", source: "scf_official_strm_bundle_2026.1" }
```

Não há `framework_code`. E um `fde_code` sozinho não identifica um requisito: dois
focal documents diferentes podem publicar "AC-1".

A rota irmã `/scf/strm` traz `framework_code`. Provavelmente é só o `select` desta
que ficou para trás.

## B8 — a mesma rota trunca em silêncio e ignora `offset`

**Severidade: alta, e independente do B7.**

```
GET /scf/strm/control/GOV-01                      -> 200, count=100
GET /scf/strm/control/GOV-01?limit=500            -> 200, count=326
GET /scf/strm/control/GOV-01?limit=500&offset=500 -> 200, count=326
GET /scf/strm/control/AST-01?limit=500            -> 200, count=160
```

Três problemas empilhados:

1. **O default de 100 corta um resultado de 326** sem dizer que cortou — não há
   `has_more`, `total`, nem `next_cursor`. Um consumidor que não passe `limit`
   acredita que GOV-01 tem 100 relações.
2. **`offset` é ignorado.** Acima do teto de `limit`, não existe caminho para as
   linhas restantes: um controle com 600 relações perde 100, em silêncio e para
   sempre.
3. Como não dá para distinguir "500 é o total" de "500 é o teto", qualquer
   `count == limit` vira dado suspeito.

**Pedido, em ordem de preferência:** cursor nesta rota; ou `offset` funcionando;
ou, no mínimo, um `total` na resposta, para que o consumidor ao menos detecte a
perda e recuse o dado.

## B2 — `GET /scf/controls/by-code/{code}` responde 500

**Severidade: alta.**

```
GET /scf/controls/by-code/GOV-01                  -> 400 "Missing query parameter: version."
GET /scf/controls/by-code/GOV-01?version=2026.1.1 -> 500 "Unexpected API error."
```

É a rota que resolve a instabilidade de UUID entre versões — o motivo pelo qual um
consumidor precisa chavear por `(scf_version_id, control_code)` em vez de por id.

Além do 500: o OpenAPI publicado declara `query?: never` para esta rota, mas ela
exige `version`. Um cliente gerado a partir do contrato não consegue chamá-la.

## B10 — `/scf/controls/{id}/mappings` retorna 500 e 503 sob caminhada sustentada

**Severidade: média, mas cara — e são transitórios.**

Numa caminhada completa do crosswalk respeitando o limite de 120 req/60s:

```
1392 controles caminhados, 76 falhas
  PES-07.3  503
  PRI-11    500
  PRI-18    503
  PRI-19.1  500
  CHG-02.2  fetch failed
```

**76 de 1.468 — cerca de 5%** — espalhadas ao longo de ~4 horas, não em rajada.
Não é rate limit: esse responde 429, e o `x-ratelimit-remaining` foi respeitado.

**Confirmamos que são transitórios.** Re-andando só os controles vazios, a segunda
passada deixou 6 falhas e a terceira zerou — os mesmos controles que retornavam
500 responderam 200 sem nenhuma mudança do lado do cliente. Sugere timeout de
conexão ou esgotamento de pool sob carga sustentada, que vocês veem nos logs e o
consumidor não.

O impacto é maior que 5% sugere: um controle que falha fica sem mapeamento
nenhum, e isso é indistinguível de um controle que legitimamente não tem nenhum.
Só se percebe a diferença guardando a lista de falhas e re-andando.

**Some sozinho se o B1 for corrigido** — uma listagem paginada faz dezenas de
requisições no lugar de 1.468.

## B3 — `limit` ignorado numa rota, 400 mudo em outra

```
GET /scf/frameworks?limit=100&after=  -> 200, 250 itens, pagination: null
GET /scf/strm?limit=1000              -> 400 "Request validation failed."
```

A primeira devolve o catálogo inteiro ignorando `limit` e sem `pagination`, o que
impede paginação e leva o consumidor a assumir que 250 é o total — hoje é, mas por
sorte.

A segunda recusa sem dizer qual é o teto. O corpo do 400 deveria nomear o campo e
o limite aceito.

## B4 — `relationship_strength` indistinguível de um default

Numa amostra de 64 linhas STRM: `0.500` × 37, `1.000` × 14, `0.800` × 11,
`0.300` × 1, `0.000` × 1.

O `0.500` era o valor que o `(parseFloat(row.relationship_strength) || 0.5)`
produzia quando o parse falhava. Há variação real agora, então o bug de origem
parece corrigido — mas **um `0.500` continua não dizendo se foi medido ou se
falhou o parse**, e não há campo que distinga.

Um consumidor prudente acaba ignorando o campo inteiro, que é desperdício de um
dado que vocês têm.

**Pedido:** omitir o campo quando não houver valor de origem, ou publicar quantas
linhas da edição 2026.1 têm `0.500` genuíno. Um dos dois resolve.

Nota menor: `relationship_strength` chega como string (`"0.500"`) enquanto `count`
chega como number. Não é bug, mas obriga todo cliente a converter.

## B5 — `framework_code` com erro de digitação, sendo chave primária

```
framework_code: "amaericas-can-osfi-self-assessment"
framework_name: "Canada - OSFI Cyber Security Self-Assessment Guidance"
```

"amaericas" está escrito errado. Isso importa mais do que um typo comum porque a
resposta à nossa Q13 estabeleceu `framework_code` como parte de chave primária, e
consumidores persistem esse valor.

**Corrigir é quebra de chave.** Precisamos saber antes: vai ser corrigido? Em qual
versão? Haverá alias do código antigo? Se não for corrigido, ele vira permanente e
paramos de tratá-lo como erro.

## B6 — Contagens divergentes entre documentação e API

| fonte | controles | frameworks |
|---|---|---|
| medido em 2026-09-09 (NDJSON + `/scf/frameworks`) | **1.468** | **250** |
| medido em 2026-08-27 | 1.473 | 272 |

Não é pedido de correção — é pergunta: **os 22 frameworks e os 5 controles que
saíram entre 27/08 e 09/09 foram removidos de propósito?** Se um framework sai do
catálogo, um assessment que o citava fica sem denominador, e um consumidor precisa
saber se isso é normal ou acidente.

## Superfície bem resolvida, que vale registrar

Nem tudo aqui é defeito. Três coisas foram medidas e estão certas:

**A re-importação do STRM funcionou.** `relationship_type` agora varia de verdade —
numa caminhada completa, `intersects` 39.185, `null` 14.819, `subset` 8.391,
`equal` 4.796, `superset` 43 — e cada linha traz `source` e `rationale`. Os 22,0%
de `null` batem exatamente com os 22% previstos no runbook de vocês, e
`equal + subset = 13.187` é o número que ele cita. Duas medições independentes
chegando ao mesmo lugar.

**`/scf/controls/{id}/mappings` está íntegro.** `framework_code` preenchido em
100% das linhas, `scf_framework_id` resolvido, e `relationship_strength` **omitido**
quando não há valor em vez de um `0.500` inventado. As três correções que mais
pediríamos chegaram juntas.

**O `null` é honesto.** Uma relação que o bundle não cobre fica nula em vez de
virar `intersects`. É a diferença entre "não sabemos" e "sabemos que se
sobrepõem", e ela agora existe no dado.

## Uma pergunta de arquitetura, que não é achado

A API oferece `/assessments/{id}/projection/{frameworkId}` e
`/intelligence/compliance-score`, e ao mesmo tempo serve o crosswalk cru para quem
quiser projetar do seu lado.

**Onde vocês pretendem que a projeção por framework viva?**

Não é pergunta retórica. Uma projeção é uma soma sobre três coisas: os mapeamentos
(de vocês), os vereditos de evidência (do consumidor) e **a política que decide o
que cada tipo de relação contribui** — se `subset` satisfaz um requisito, se
`intersects` exige revisão humana, se `null` conta como nada. Essa política é onde
mora o julgamento de conformidade e a responsabilidade por ele.

Se ela vive na API, todo cliente recebe a mesma decisão, e nenhum deles pode
defender diante de um auditor um número que não formulou. Se vive no consumidor, a
API precisa ser excelente em servir o dado — crosswalk paginável, `by-code`
funcionando, Anexo A presente — e pode parar de calcular índices.

Vocês já removeram um índice de conformidade fabricado por ADR própria. O instinto
parece certo. Vale tornar a posição explícita, porque ela muda o que cada
consumidor constrói.
