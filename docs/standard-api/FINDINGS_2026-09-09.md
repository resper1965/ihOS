# Achados da ihOS contra a API reformulada — 2026-09-08

> Entregar este arquivo inteiro ao time/agente do `standard-api`. Tudo abaixo foi
> medido contra `https://standard-api.bekaa.eu/api/v1` em 2026-09-08, com a chave
> nova emitida para a ihOS, sem header `x-standard-tenant-id`. (Se precisarem
> correlacionar as requisições nos logs de vocês, pedimos o prefixo por canal
> separado — não vai em documento.)
> Reprodução: `npm run probe:standard-api` na ihOS.

---

## Contexto

A ihOS consome esta API como **espinha única**: não existe mais catálogo de
controle local (o `iso27001-annex-a.json` foi deletado). Todo controle, framework
e crosswalk vem daqui. Se um número aqui é inventado, a ihOS o publica.

Antes de qualquer coisa: **o re-import STRM chegou em produção hoje**
(`imported_at: 2026-09-08T17:51:20Z`, `version_label: 2026.1.1`,
`import_status: succeeded`, `is_synthetic: false`). O runbook
`docs/runbooks/strm-reimport.md` ainda diz *"applied locally; staging and
production not yet run"* — está desatualizado e induz ao erro quem for planejar
em cima dele.

E a correção principal funcionou: `relationship_type` agora varia
(51 `intersects` / 8 `equal` / 5 `subset` numa amostra de 64) e cada linha traz
`source: "scf_official_strm_bundle_2026.1"` e `rationale`. O `intersects`
fabricado em 79.127 de 79.133 linhas acabou. Isso destrava a curadoria da ihOS.

Os achados abaixo são o que ainda impede o consumo.

---

## B1 — `GET /scf/strm` devolve menos linhas que um único controle

**Severidade: alta, não bloqueante.** É o endpoint que a ihOS quer usar para
substituir a caminhada de ~64 minutos controle a controle. Não bloqueia porque
`/scf/controls/{uuid}/mappings` — o endpoint antigo — já serve o dado corrigido
e completo (ver "O que já funciona", no fim). Mas enquanto `/scf/strm` não
paginar, a caminhada de 64 minutos continua sendo o único caminho.

```
GET /scf/strm?limit=100&offset=0                        -> 200, count=64
GET /scf/strm?limit=100&offset=100                       -> 200, count=0
GET /scf/strm?scf_version_id=826a1f05-…-ced8019a6701     -> 200, count=64
GET /scf/strm?relationship_type=equal&limit=100          -> 200, count=8
GET /scf/strm/control/GOV-01                             -> 200, count=100
```

Um controle sozinho (`GOV-01`) devolve **100** linhas; a listagem da versão
inteira devolve **64**. O bundle carregou 53.664. A listagem está filtrando por
algo que não está documentado — provavelmente `organization_id`, que as linhas
STRM carregam e que a busca cruza com a org da chave, enquanto a rota por
controle não cruza.

Se for isso, a pergunta de produto é: **por que uma linha do bundle oficial da
SCF é escopada por organização?** Ela é catálogo, não dado do cliente.

**O que a ihOS precisa:** que `/scf/strm` pagine as ~53.664 linhas da versão,
filtrável por `framework_id`, com um cursor estável.

## B2 — `GET /scf/controls/by-code/{code}` responde 500

**Severidade: alta.** É o endpoint que resolve a instabilidade de UUID entre
versões — o motivo pelo qual toda chave persistida na ihOS é
`(scf_version_id, control_code)`.

```
GET /scf/controls/by-code/GOV-01                  -> 400 "Missing query parameter: version."
GET /scf/controls/by-code/GOV-01?version=2026.1.1 -> 500 "Unexpected API error."
```

Além do 500: o OpenAPI publicado declara `query?: never` para esta rota, mas a
rota exige `version`. Ou o parâmetro entra no documento, ou some da rota. Hoje
um cliente gerado a partir do contrato não consegue chamá-la.

## B3 — `limit` em `/scf/frameworks` é ignorado; `limit=1000` em `/scf/strm` dá 400 mudo

```
GET /scf/frameworks?limit=100&after=  -> 200, 250 itens, pagination: null
GET /scf/strm?limit=1000              -> 400 "Request validation failed."
```

A primeira devolve o catálogo inteiro ignorando `limit` e sem `pagination`, o
que impede paginação e faz o cliente assumir que 250 é o total (hoje é, mas isso
é sorte). A segunda recusa sem dizer qual é o teto — o corpo do 400 deveria
nomear o campo e o limite aceito.

## B4 — `relationship_strength` ainda é indistinguível de um default

Na amostra de 64: `0.500` × 37, `1.000` × 14, `0.800` × 11, `0.300` × 1,
`0.000` × 1.

O `0.500` era o valor que o `(parseFloat(row.relationship_strength) || 0.5)`
produzia quando o parse falhava. Agora há variação real, então o bug de origem
parece corrigido — mas **um `0.500` continua não dizendo se foi medido ou se
falhou o parse**, e não há campo que distinga. A ihOS ignora `strength` por
completo na política de curadoria por causa disso.

**Pedido:** ou omitir o campo quando não houver valor de origem, ou publicar
quantas linhas da edição 2026.1 têm `0.500` genuíno. Um dos dois resolve.

Nota relacionada: `relationship_strength` chega como **string** (`"0.500"`),
enquanto `count` chega como number. Não é um bug, mas obriga todo cliente a
converter.

## B5 — `framework_code` com erro de digitação, e ele é chave primária

```
framework_code: "amaericas-can-osfi-self-assessment"
framework_name: "Canada - OSFI Cyber Security Self-Assessment Guidance"
```

"amaericas" está escrito errado. Isso importa mais do que parece: a resposta à
nossa Q13 estabeleceu `framework_code` como parte da chave primária, e a ihOS
persiste esse valor na tabela `framework_identity_curation`, onde uma pessoa
assina qual framework do catálogo o slug local significa.

**Corrigir o typo é uma quebra de chave.** Precisamos saber, antes: vai ser
corrigido? Se sim, em qual versão, e haverá alias do código antigo? Se não, ele
vira permanente e paramos de tratá-lo como erro.

## B9 — `framework_code` mudou de frase humana para slug, e isso invalidou toda a curadoria

**Severidade: já não nos bloqueia — e é por isso que vocês deveriam olhar.**

Quando escrevemos isto, bloqueava. Em 2026-09-09 contornamos do nosso lado,
recurando as oito identidades contra os slugs novos, então a ihOS voltou a
funcionar sem nenhuma ação de vocês.

Priorizem pela razão certa: **a mudança foi silenciosa.** Nenhum erro, nenhum
aviso, nenhuma nota de versão. Uma projeção passou a somar sobre conjunto vazio,
que é indistinguível de um framework que ninguém avaliou. Nós só descobrimos
onze dias depois, medindo à mão. Qualquer cliente de vocês que chaveie por
`framework_code` — e a resposta de vocês à nossa Q13 estabeleceu esse campo como
parte de chave primária — teve a mesma quebra e provavelmente ainda não sabe.

Em 27/08 o `CONTRACT_AUDIT.md` registrou, medido: *"o `framework_code` do vendor
é uma frase humana, não um slug — ex. `AICPA TSC 2017:2022 (used for SOC 2)`"*.
Hoje a mesma chave vem assim:

```
framework_code: "general-aicpa-pmf-2020"
framework_name: "AICPA Privacy Management Framework (PMF)"
```

A frase humana migrou para `framework_name` e `framework_code` virou slug. Faz
todo sentido como modelagem — mas a resposta à nossa **Q13** estabeleceu
`framework_code` como **parte da chave primária**, e nós persistimos esse valor
em `framework_identity_curation`, onde uma pessoa assina qual framework do
catálogo cada slug local significa.

Resultado medido agora, contra a versão `826a1f05…`:

| local_code | valor curado em 28/08 | linhas que casam hoje |
|---|---|---|
| iso27001 | `ISO 27001 2022` | **0** |
| soc2 | `AICPA TSC 2017:2022 (used for SOC 2)` | **0** |
| nist_800_53 | `NIST 800-53 R5` | **0** |
| EU-GDPR | `EMEA EU GDPR` | **0** |
| BR-LGPD | `Americas Brazil LGPD` | **0** |
| EU-DORA | `EMEA EU DORA` | **0** |
| iso27701 | `ISO 27701  2025` | **0** |
| TX-LEVEL-2 | `US - TX TX-RAMP Level 2` | **0** |

As oito identidades, todas assinadas por uma pessoa em 28/08, apontam para
valores que não existem mais. Nenhum framework projeta. E como a mudança foi
silenciosa, nada quebrou de forma visível — a projeção apenas passaria a somar
sobre zero linhas.

**O que pedimos, e é barato:** que uma mudança de forma em `framework_code`
seja tratada como quebra de contrato — nota em `CHANGELOG.md`, e de preferência
um período em que `framework_name` e o código antigo ainda resolvam. Uma chave
primária que muda de vocabulário sem aviso é indistinguível, do lado do
cliente, de um catálogo que perdeu 250 frameworks.

**Pergunta direta:** o slug é agora estável entre versões de SCF, ou ele também
pode mudar num próximo import? A resposta decide se voltamos a curar contra
`framework_code` ou se passamos a curar contra `framework_id` (UUID) com uma
releitura a cada versão.

## B10 — `/scf/controls/{id}/mappings` retorna 500 e 503 sob caminhada sustentada

**Severidade: média, mas cara.** Medido hoje, numa caminhada completa do
crosswalk respeitando o limite de 120 req/60s:

```
done: 1392 controls, 63493 mappings stored, 76 failures
  CHG-02.2   fetch failed
  PES-07.3   503
  PRI-11     500
  PRI-18     503
  PRI-19.1   500
```

**76 de 1.468 controles falharam — cerca de 5%** — e não em rajada: espalhados
ao longo de ~4 horas. Não é rate limit (esse responde 429 e nós respeitamos o
`x-ratelimit-remaining`); são erros de servidor.

O impacto do lado do cliente é maior do que 5% sugere: um controle que falha
fica sem nenhum mapeamento, e um controle sem mapeamento é indistinguível de um
controle que legitimamente não tem nenhum. Só descobrimos a diferença porque o
nosso sync guarda a lista de falhas e sabe re-andar apenas os controles vazios.

**São transitórios, e nós confirmamos.** Re-andamos só os controles vazios: a
segunda passada deixou 6 falhas (`SAT-03.8`, `SEA-03.2`, `SEA-09`, `SEA-13`,
`SEA-14.1`…), e a terceira passada **zerou** — os mesmos controles que
retornavam 500 responderam 200 sem nenhuma mudança do nosso lado. Não é dado
que quebra a rota; é instabilidade sob carga.

**Pedido:** logs do lado de vocês para essa janela. Um 500 transitório a ~5%
sugere timeout de conexão com o banco ou esgotamento de pool sob caminhada
sustentada — coisa que vocês veem e nós não.

**O resultado final, para vocês compararem com o runbook de vocês:** 67.234
mapeamentos sobre 1.390 de 1.468 controles (78 controles não têm nenhum
mapeamento no crosswalk oficial — isso parece correto, não uma falha nossa).
Distribuição: `intersects` 39.185, **`null` 14.819 (22,0%)**, `subset` 8.391,
`equal` 4.796, `superset` 43. Os 22,0% de `null` batem com os 22% que o runbook
de vocês previu, e `equal + subset = 13.187` é exatamente o número que ele cita.
Duas medições independentes chegando ao mesmo lugar — o re-import está fiel.

Nota: isto some sozinho se o B1 for corrigido. Uma listagem paginada de
`/scf/strm` faz dezenas de requisições no lugar de 1.468, e menos requisições é
menos superfície para o erro.

## B11 — O Anexo A da ISO 27001 não existe no catálogo de vocês

**Severidade: é a maior lacuna comercial deste documento, não um defeito.**

Verificado em 2026-09-09 por três caminhos independentes:

1. **250 frameworks no catálogo, um único de ISO 27001** — `general-iso-27001-2022`.
   Não há um segundo framework para o Anexo A. (Os dois que trazem "Annex" no nome
   são o CRA e o NIS2 da UE, sem relação.)
2. **`GET /scf/strm/lookup?fde_code=…` para seis códigos cobrindo os quatro temas**
   — `A.5.1`, `A.5.15`, `A.6.3`, `A.7.1`, `A.8.1`, `A.8.34`: todos `200` com
   `count = 0`. Nenhum dos 183 focal documents do bundle STRM carrega um código
   `A.x.y`.
3. **`GET /scf/frameworks/{id}/requirements` do próprio framework**: 148
   requisitos, **zero** com prefixo `A.`. São `4.4`, `5.1`, `5.1(a)`, `6.1.2(d)(3)`,
   `10.2(b)(2)` — o sistema de gestão inteiro, e só ele.

O que vocês publicam como ISO 27001 são as cláusulas 4 a 10. O Anexo A — os 93
controles de segurança da edição 2022 — não está em lugar nenhum da API.

**Por que isso importa mais do que um endpoint quebrado.** Uma organização
certificada declara sua postura numa Declaração de Aplicabilidade, e uma SoA é
indexada por Anexo A, não por cláusula de gestão. A nossa tem 93 linhas, uma por
controle do Anexo A, com aplicabilidade e justificativa. É o artefato mais
autoritativo que um SGSI produz.

Quer dizer que, para o caso de uso mais comum de um cliente de vocês — "aqui
está a minha SoA, me diga o que ela cobre" — o crosswalk de vocês não tem por
onde começar. As cláusulas de gestão respondem "vocês têm um SGSI?"; o Anexo A
responde "quais controles vocês aplicam?", que é a pergunta que hospital,
auditor e questionário de segurança fazem.

**Como resolvemos do nosso lado**, para vocês saberem o tamanho do que falta:
construímos um crosswalk proprietário Anexo A → SCF. 125 ids, 2.228 linhas,
alcançando 407 controles SCF — todos os 407 existem no catálogo de vocês. Ele
cobre os 93 controles do Anexo A da 27001:2022 e os 31 do Anexo A da 27701:2019.
Medido contra a nossa SoA: 119 dos 127 controles aplicáveis alcançam o SCF por
2.149 ligações.

Não estamos pedindo que copiem o nosso — a proveniência dele é nossa e não
documentada. Estamos dizendo que a lacuna é dessa ordem de grandeza e que dá
para fechá-la.

**Perguntas:** o Anexo A ficou de fora por licenciamento, por decisão de escopo,
ou por não ter chegado ainda? E o Anexo B do 27701 (`B.8.2.1`…) tem o mesmo
status? No nosso caso são 8 controles aplicáveis sem caminho até a espinha, e é
a única lacuna de cobertura que sobrou depois de tudo o mais.

## B7 — `/scf/strm/control/{code}` não diz a qual framework a linha pertence

**Severidade: torna a rota inutilizável para o nosso caso.** A resposta traz
apenas `fde_code`/`fde_name`, sem `framework_code`:

```
GET /scf/strm/control/GOV-01?limit=500  -> 200, count=326
row: { strm_id, fde_code: "03.15.01.A", fde_name: "Policy and Procedures",
       relationship_type: "subset", relationship_strength: "1.000",
       rationale: "Functional", source: "scf_official_strm_bundle_2026.1" }
```

Um `fde_code` sozinho não identifica um requisito: dois focal documents
diferentes podem publicar "AC-1". Sem o framework não há denominador, e a linha
não pode sequer ser chaveada — `framework_code` é parte da chave primária que a
resposta à nossa Q13 estabeleceu.

A rota irmã `/scf/strm` (B1) traz `framework_code`. Provavelmente é só o `select`
desta rota que ficou para trás.

## B8 — `/scf/strm/control/{code}` trunca em silêncio e ignora `offset`

**Severidade: alta.** Independente do B7, e vale para qualquer cliente que use
esta rota.

```
GET /scf/strm/control/GOV-01                      -> 200, count=100
GET /scf/strm/control/GOV-01?limit=500            -> 200, count=326
GET /scf/strm/control/GOV-01?limit=500&offset=500 -> 200, count=326
GET /scf/strm/control/AST-01?limit=500            -> 200, count=160
```

Três problemas empilhados:

1. **O default de 100 corta um resultado de 326** e a resposta não diz que
   cortou — não há `has_more`, `total`, nem `next_cursor`. Um cliente que não
   passe `limit` acredita que GOV-01 tem 100 relações STRM. Tem 326.
2. **`offset` é ignorado.** `offset=500` devolve as mesmas 326 linhas. Então
   acima do teto de `limit` (500) **não existe caminho para as linhas
   restantes**. Um controle com 600 relações perde 100 de forma permanente e
   silenciosa.
3. Como o cliente não consegue distinguir "500 é o total" de "500 é o teto",
   qualquer `count == limit` vira dado suspeito.

Isto é exatamente a classe de defeito que a re-importação STRM veio corrigir: um
número que parece completo sem ser. Antes era o `intersects` fabricado; agora é
uma contagem truncada. O impacto é o mesmo — a ihOS publica um denominador
errado sem ter como saber.

**Pedido mínimo, em ordem de preferência:** (a) paginação por cursor nesta rota;
ou (b) `offset` funcionando; ou (c) na pior das hipóteses, um `total` na
resposta, para que o cliente ao menos detecte a perda e recuse o dado.

## O que já funciona — e é a notícia mais importante daqui

`GET /scf/controls/{uuid}/mappings`, o endpoint que a ihOS já consumia, **herdou
a correção do STRM e está íntegro.** Medido em GOV-01, 2026-09-08:

| | |
|---|---|
| Linhas | 416, todas com `framework_code` preenchido |
| `relationship_type` | `subset` 285, `intersects` 30, **`null` 101** |
| `scf_framework_id` | preenchido (era `""` hardcoded) |
| `relationship_strength` | **ausente do payload**, em vez de um `0.500` falso |
| `is_official` / `is_synthetic` | `true` / `false` |

As três correções que mais pedimos chegaram juntas: o operador é real, o `null`
é honesto em vez de virar `intersects`, e a força ausente é omitida em vez de
inventada. `limit` e `offset` são ignorados e a resposta vem completa — não é
paginação, mas para este caso é o comportamento seguro.

**Consequência prática:** a ihOS não precisa de nenhuma mudança de código para
consumir o dado corrigido. O re-walk foi disparado hoje contra a versão
`826a1f05…` usando este endpoint. Os itens B1–B8 são o que falta para reduzir os
64 minutos e para abrir a superfície nova — não são pré-requisito.

## O que a ihOS vai fazer com a resposta

1. **Feito hoje, sem depender de vocês:** re-walk completo contra a versão
   `826a1f05…` via `/scf/controls/{uuid}/mappings`. As 79.133 linhas antigas
   ficam órfãs da versão anterior (`8260df81…`) e serão removidas depois.
2. Reativar a política de curadoria, que grada `equal`/`subset` → *satisfies*,
   `intersects` → *needs_review*, `null` → *unrecorded*. Ela já está escrita e
   testada; estava inerte porque 100% das linhas eram `intersects`.
3. Reescrever o sync sobre `/scf/strm` paginado por framework, para cair de 64
   minutos para minutos — depende de **B1**.
4. Trocar a resolução de controle por `by-code` — depende de **B2**.

## Superfície que a ihOS ainda não consome (não é achado, é oportunidade)

Dos 351 paths publicados, a ihOS chama 11. Os que mais mudariam o produto:

- `/scf/controls/{id}/assessment-objectives` e `/evidence-requests` — hoje a
  ihOS avalia cada controle por RAG contra os documentos do cliente, inventando
  o critério. Esses endpoints são o critério.
- `/scf/controls/{id}/maturity-criteria`, `/threats`, `/risks`
- `/assessments/{id}/projection/{frameworkId}` — projeção do lado da API.
  Precisamos entender se ela substitui ou concorre com a projeção local; duas
  projeções discordando na frente do cliente é pior que nenhuma.

**Pergunta de arquitetura, e é a mais importante deste documento:** a projeção
por framework deve viver na API ou na ihOS? Hoje existe dos dois lados. Se for
da API, a ihOS deleta `src/lib/assessment/projection.ts` e a política de
curadoria junto — mas aí a curadoria de identidade de framework, que é uma
decisão assinada por uma pessoa, precisa de um lugar na API para morar.
